---
name: implementation
description: Implement a task, then review and fix it in a bounded loop, and write a reviewer-oriented implementation report
disable-model-invocation: true
---

Orchestrate the implementation of the task supplied with this invocation. Never edit project files yourself.

Inputs:

- **Task**: the `task.md` file supplied with the invocation. Without one, implement the whole plan.
- **Plan**: the plan the task file links to, else the supplied plan path, else `plan.md` beside the task file. Without a plan, implement from the task file alone. If an explicitly linked or supplied plan is missing, multiple plans are ambiguous, or neither a task nor a plan is available, stop and report it as a blocker.
- **Artifact dir**: the task file's directory, else the plan's.
- **Contract**: `api-contract.md` in the artifact dir, when present. Its entry points, types, errors, exports, and tests are approved; any change to them is an unapproved API decision.
- **Settled decisions**: `settled.md` in the artifact dir. Read it if present; otherwise create it before the first implementer run. You own it and update it after each round and user decision. Record only names and structures explicitly accepted or rejected, with their scope, reason, and decision source or round; a rejected finding alone does not settle its proposed alternative. Preserve earlier decisions and record any superseding decision with its reason. Pass the current file to every implementer and reviewer, including style-pass reviewers, as binding context. A reversal requires evidence of a concrete defect, not preference. It cannot override the task or contract.

Responsibilities:

- **Orchestrator**: read the task, plan, contract, and settled decisions to establish scope and required evidence. Own dispatch, snapshots and diff measurements, validation gates, review synthesis, user decisions, accumulated findings, the final report, and commit. Use worker and reviewer evidence for these duties; request missing or contradictory evidence from its producer. Inspect source only to resolve a specific uncertainty about scope, a finding, or a report claim. Do not independently explore implementation approaches or rerun the implementer's validation.
- **Implementer**: own source exploration, implementation choices within approved scope, edits, and required validation. May launch subagents for read-only source exploration, research, and validation while remaining the sole writer. Supply enough evidence for the orchestrator to assess completion and write the report without repeating that investigation.
- **Reviewers**: independently inspect changed code and relevant surrounding code under `review/SKILL.md`. May launch read-only helper subagents within their assigned review scope and remain responsible for the final findings. Shared reads of task context and independent review of source are intentional.

Rules:

- Only one writer subagent runs at a time; wait for each to finish.
- Before every implementer dispatch, including fixes, validation retries, and the style pass, read and follow [model-selection](../model-selection/SKILL.md). Apply its selection through the host's available controls and record the stage, selection reason, and actual worker model ID and effort from execution metadata; mark unobservable values as unknown.
- Resume the same implementer for fixes, validation retries, and the style pass. Let auto-compaction preserve continuity as context grows. Replace it only if it is unavailable or repeatedly fails to incorporate an explicit, evidence-backed correction.
- For repeated reasoning failures, use a fresh worker without inherited conversation history and escalate to a higher model weight under model-selection; increasing effort alone is insufficient. Record the failed correction and escalation reason. If no higher weight is available, report that limit. Every replacement receives a concise handoff with the task, plan, contract, and current settled-decision paths as applicable, current implementation state and retained evidence, accepted findings and failed approaches, and required validation. Replacement does not reset the review-round limit.
- Accumulate incomplete or deferred work from every implementer run and deferred or unresolved review findings from every round, with their location evidence and reasons, removing an item only when later evidence shows it resolved.
- Retain the implementer's evidence handoff and subsequent updates, bound to their reported tracked and untracked code state. After worker, hook, or external edits, compare the current state with the evidence's state and request refreshes of affected claims and validation from the implementer. Carry forward unaffected evidence. Resolve missing or contradictory report evidence through targeted questions to its producer; do not start a separate implementation investigation or require a full handoff rewrite. Evidence-only follow-ups do not replace the most recent implementation run for edit comparisons or add a review round; project edits remain subject to the existing review workflow.
- Adjacent cleanups are in scope when the implementer's handoff shows they meet the allowance in `implementer.md`. Check the budget and the contract from the handoff and `git diff --stat`; send violations back. Never treat a conforming cleanup as scope expansion or defer it.
- If an unapproved product, API, architecture, or scope decision comes up, stop and ask the user.
- Validation gate: before review or the implementation report, the writer must show the commands run and passing results for every required test: the verification of each acceptance criterion and, with a contract, all its tests. Missing, skipped, failing, or deferred tests go back to the writer. If validation is blocked, ask the user; never waive it.
- Validation timing: before review, require fast validation to pass. Expensive checks may wait until review findings are resolved. Before the implementation report and commit, require all repository-required checks to pass on the final relevant state. Reuse evidence when that state is unchanged.
- Successful exit: `No new actionable findings`, `No new edits`, or `Post-style passed`, with all required validation passing, no remaining "fix now" findings or open user decisions, and no incomplete task requirements.

Workflow:

Before any check or possible exit, remove any `small-change.txt` from the artifact dir. If the dir cannot be resolved or the marker cannot be removed, stop and report the blocker.

1. Run `git status --porcelain --untracked-files=all`. If the working tree is not clean, ask the user how to proceed: the review scope is uncommitted work, so pre-existing changes would be reviewed as part of the task. Record the approved task diff baseline and snapshot the tracked and untracked state before the first implementer run.
2. Launch a fresh `worker` told to read and follow [implementer.md](./implementer.md), with the plan path if any, the task file, the contract path if any, the task diff baseline, and required tests. Retain its evidence handoff and apply the validation gate.
3. Review/fix loop, at most 6 rounds:
   Before each round, compare the current tracked diff and untracked file contents with their state before the most recent implementer run. If that run made no edits, or no uncommitted changes remain, exit `No new edits` without invoking the review skill.
   a. Read [review/SKILL.md](../review/SKILL.md) as a file and follow its instructions. Do not call the Skill tool for `review`: it is `disable-model-invocation` and reserved for explicit user invocation. Run it with no fixed point, so it reviews uncommitted work, with the previous round's snapshot if any, and with the plan path and the task file as its intent: the task's acceptance criteria, scope edges, and constraints, not the hints in its notes, so an approach that meets the criteria differently is not a finding. Stylistic findings get the same classification and resolution criteria as any other; never downgrade or defer one for being stylistic. The exception is comment wording, which the review skill classifies by whether the comment's content is wrong. Pass the implementer's adjacent-cleanup list too, and tell reviewers to check each against the allowance conditions in `implementer.md` rather than whether it was requested: a conforming cleanup is never scope expansion, while a violating one (behavior change, over budget, contract or settled conflict) is a "fix now" finding, usually to revert it. With a contract, pass it as settled: a finding that would change it is "needs user decision" or rejected as scope expansion, never "fix now".
   b. Bring "needs user decision" findings to the user. Update settled decisions before handing off or exiting. With no "fix now" findings, exit `No new actionable findings`. If every "fix now" finding is stylistic (it changes form, never behavior) or touches only workflow artifacts in the artifact dir (not the repository), and no user decision is open, go to d. After round 6, exit `Review cycle limit reached`.
   c. Resume the implementer, subject to the replacement rules, with the accepted findings and their `path:line` evidence, asking for no unrelated changes. Apply the validation gate. Check that the path of every finding inside the repository appears in `git diff --stat` or `git ls-files --others --exclude-standard`, and that the report shows command output of the changed lines for each finding; send any missing finding back to the implementer. Start the next round.
   d. Style pass, allowed after round 6 and not counted as a round:
      1. Snapshot the tracked and untracked state, and the workflow artifacts the findings touch.
      2. Resume the implementer, subject to the replacement rules, for these style fixes only. Apply the validation gate; retries share the snapshot.
      3. Launch a `reviewer` following [precommit-reviewer.md](../review/precommit-reviewer.md).
      4. Launch a fresh `reviewer` following [post-style.md](./post-style.md) with the findings, the snapshot, the current state, and the validation and hook results.
      5. On `pass`, exit `Post-style passed`. Otherwise, retain its findings: with rounds remaining, return to c treating them as non-stylistic; after round 6, exit `Post-style failed`.
4. Confirm retained report evidence covers the final task state, resolving affected, missing, or contradictory claims through targeted requests. Apply the validation gate. Read and follow [implementation-writer.md](./implementation-writer.md) directly, assembling `implementation.md` in the artifact dir from the implementer's handoff and updates plus reviewer evidence. Supply the plan path if any, the task, the contract path if any, and the orchestrator-owned inputs: worker model/effort history with execution evidence, final changed files, the adjacent cleanups with their measured additions and deletions, accumulated deferred and unresolved items, review outcomes and dispositions, the full review-round count, any post-style result, the loop exit reason, the final task diff's additions and deletions with the baseline and measurement commands/results (or that they are unmeasurable), and provisional success eligibility with evidence. Derive completion and Small change verdicts from these inputs; do not reconstruct the implementation explanation or risks through a new source investigation.
5. On a successful exit with the report written, commit the task's changes using a Conventional Commits message.
6. Create a zero-byte `small-change.txt` in the artifact dir only once the commit has settled: the report's Small change is `yes`, the commit succeeded, and `git status --porcelain --untracked-files=all` then shows no left-over changes. Otherwise leave no marker.
7. On a successful exit after 4 or more review rounds, read and follow [the retro skill](../retro/SKILL.md) for the current implementation session. Use the full review-round count; the style pass does not count as a round.
8. Report the implementation report path, whether `small-change.txt` was created, the retro report path if triggered, and `Exit reason: <loop exit reason>`.
